# like-bot-v2 설계

작성일: 2026-08-30
대상: 레거시 `legacy/` (PyQt6 + Selenium)의 재작성
상태: 확정 — 구현 계획 수립 대기

---

## 1. 목적

이 도구는 **운영자 자신의 블로그로 유입을 늘리기 위해** 존재한다. 수단은 물량이 아니라
상호성이다.

> 운영자가 다른 사람의 블로그를 방문해 관심을 표시(공감)하면,
> 그 블로그 주인이 답방하여 운영자의 블로그를 보게 된다.

설계상의 모든 판단이 이 한 문장에서 나온다.

- **공감을 누르는 계정은 운영자 본인의 블로그 계정 하나여야 한다.** 답방은 공감을 누른
  주체에게 돌아온다. 여러 계정으로 나누면 유입이 여러 블로그로 흩어져 목적을 잃는다.
- **주제·기간 타겟팅은 답방률을 높이기 위한 것**이지 "아무 블로그나 찾기"가 아니다.
  최근에 해당 주제로 글을 쓴 사람은 지금 활동 중이고 관심사가 겹치는, 답방 확률이
  가장 높은 모집단이다.
- **깊이보다 폭이 낫다.** 적은 수의 블로그에 많이 누르는 것보다, 많은 블로그에 조금씩
  누르는 쪽이 답방을 더 많이 만들고 스팸처럼 보이지도 않는다.
- **계정 안전은 부가 요구사항이 아니라 일급 요구사항이다.** 정지된 계정의 유입은 0이다.
  계정당 공감 속도를 올리는 모든 선택은 속도 제한으로 대가를 치러야 한다.

### 성과 지표

답방을 유도하는 단위는 **접촉한 블로그 주인 수**이지 공감 개수가 아니다. 한 블로그에
3개를 누르든 1개를 누르든 답방 기회는 1명이다. 레거시가 목표를 공감 개수로 잡은 것은
목적과 어긋난 지표였다.

## 2. 확정된 설계 결정

### 결정 1 — BFS 제거

공감자 그래프 확장(`SympathyHistoryList` 순회)을 전면 폐기한다. 검색 결과를 순회하며
블로그당 N개를 공감하는 것이 전부다.

폐기 대상: `get_buddy_ids`, `extract_buddy_info`, `Depth` 입력, `except bot` 체크박스,
`SympathyHistoryList` 접근 전체.

### 결정 2 — 순회 범위: 결과 끝까지

페이지 번호를 1부터 올리며 블로그 링크가 0건인 페이지를 만나면 종료한다. 사용자가
페이지 범위를 지정하지 않는다.

### 결정 3 — Playwright (Selenium 대체)

단, 실측 결과 브라우저가 필요한 작업은 **공감 클릭 하나뿐**으로 축소되었다(§3 참조).
Playwright를 쓰는 이유는 `frame_locator("#mainFrame")`로 iframe 전환 상태 관리를
없애고, auto-waiting으로 산재한 `time.sleep`을 제거하며, `storage_state`로 로그인
구간을 우회하고, chromedriver 버전 관리를 없애기 위함이다.

### 결정 4 — 병렬은 키워드별, 계정별이 아님

계정 하나(운영자 본인 블로그)가 여러 키워드를 동시에 공략한다. 계정을 나누면 §1의
목적에 반한다.

실측 이후 이 결정의 구현 형태가 바뀌었다. 검색·글목록이 HTTP로 분리되면서 병렬은
**대상 발굴 단계에만** 존재하고, 공감은 계정 단위 속도 제한에 묶인 단일 스트림이 된다
(§5). 브라우저 탭은 **1개**다 — 탭을 늘려도 속도 제한 때문에 총 공감량이 늘지 않는다.

### 결정 5 — 종료 조건: 방문 블로그 수 상한 또는 결과 소진

먼저 오는 쪽에서 멈춘다. 상한은 워커별이 아니라 **계정 단위 전역 예산**이다. 안전의
단위가 계정이므로 워커별 상한이면 4배가 되어 무의미해진다.

### 결정 6 — 방문 기록 영구 보관

방문한 블로그 ID를 파일에 남겨 다음 실행에서 건너뛴다. 상한 N명이 "매번 새로운 N명"이
되고, 나중에 분석의 기초 데이터가 된다.

**기록의 범위는 공감을 누른 로그인 계정이다.** 계정이 다르면 방문 이력도 별개다 —
계정 B는 계정 A가 다녀온 블로그에 아직 간 적이 없기 때문이다(§6.4).

### 결정 7 — 구현 순서: 엔진 → PyQt6 데스크톱 → (나중에) 웹·리눅스

**이번 작업의 범위는 엔진 + PyQt6 데스크톱까지다.**

웹을 나중에 두는 이유는 작업량이 아니라 검증 순서다. 셀렉터 전략과 안전 속도는 눈으로
보면서(headful) 확인해야 알 수 있고, 그 검증을 마친 엔진만 headless 무인 운용에 올릴
수 있다. 검증되지 않은 엔진을 서버에 먼저 올리면 계정 정지를 며칠 뒤에 발견하게 된다.

### 결정 8 — asyncio 코어 + PyQt 브리지

**Playwright의 동기 API는 스레드 안전하지 않다.** 레거시처럼 `QThread` 4개를 쓰면 각
스레드가 별도 브라우저 컨텍스트를 가져야 하고, 같은 계정으로 로그인이 4번 일어난다.

엔진 전체를 `asyncio`로 작성한다. 단일 이벤트 루프이므로 속도 제한 토큰과 공유 방문
기록에 **락이 필요 없다** — 스레드였다면 가장 버그가 나기 쉬운 지점이다. PyQt는 별도
스레드에서 루프를 돌리고 이벤트를 시그널로 중계한다. 엔진은 PyQt를 전혀 모르므로
2단계 웹은 같은 이벤트를 웹소켓으로 흘리기만 하면 된다.

## 3. 실측으로 확인된 외부 계약

2026-08-30에 직접 호출하여 확인했다. 이 절의 내용은 추정이 아니라 관측 결과다.

### 3.1 블로그 검색 API — 비로그인 가능, 순수 JSON

```
GET https://section.blog.naver.com/ajax/SearchList.naver
    ?countPerPage=7
    &currentPage=1
    &keyword=<검색어>
    &type=post
    &orderBy=recentdate            # sim | recentdate
    &rangeType=PERIOD              # ALL | PERIOD
    &startDate=2026-08-29          # rangeType=PERIOD일 때
    &endDate=2026-08-30
헤더: Referer: https://section.blog.naver.com/Search/Post.naver
```

응답은 `)]}',\n` 접두사(XSSI 방어) 뒤에 JSON이 온다. 접두사를 제거하고 파싱한다.

```
result.totalCount        int   — 1000이 상한 (아래 참조)
result.pagePerCount      int   — 7 (고정 관측)
result.searchList[]
    .domainIdOrBlogId    str   — 블로그 ID
    .logNo               int   — 글 번호
    .postUrl             str
    .title               str   — <strong class="search_keyword"> 태그 포함
    .addDate             int   — epoch milliseconds
    .blogName            str
    .nickName            str
```

**`totalCount`의 1000은 네이버가 거는 상한이다.** 좁은 키워드에서는 실제 값이 나온다
(`부산 사상구 필라테스 재등록` → 751). 페이지 경계 실측:

```
page 142 → 7건    page 143 → 6건    page 144 → 0건    page 200 → 0건
```

1000 ÷ 7 = 142.86 → **143페이지가 마지막**이며 실측과 정확히 일치한다.

> **레거시 진단 정정.** `core/like_thread.py`의 `count = 1000` 하드코딩과 `count // 7`로
> 인한 142페이지 상한은 네이버의 실제 한계와 일치한다. 임의의 땜빵이 아니었고, UI의
> "572페이지"가 애초에 도달 불가능한 값이었다. 초기 분석에서 이를 "조용한 잘림 버그"로
> 규정한 것은 과한 진단이었다. 다만 `totalCount`를 API에서 직접 받으면 좁은 키워드의
> 정확한 진행률을 표시할 수 있으므로, v2는 이 값을 활용한다.

### 3.2 블로그 RSS — 최신 글 목록에 사용 가능

```
GET https://rss.blog.naver.com/{blogId}.xml
→ channel/item/link  (CDATA로 감싸짐) 에서 글 번호 추출
```

검색으로 얻은 블로그 7곳 전부 성공했고, 반환 글 수는 13~50개였다. **검색에 걸린 글이
7곳 모두에서 RSS 최신 목록에 포함**되어 있었다.

`PostList.naver` DOM 파싱(레거시의 "목록열기" 버튼 클릭 → 테이블 XPath)이 불필요해진다.

### 3.3 결론: 브라우저가 필요한 작업

| 단계 | 수단 |
|---|---|
| 검색 → 블로그 발굴 | **순수 HTTP, 비로그인** |
| 블로그 → 최신 글 목록 | **순수 HTTP (RSS)** |
| 공감 클릭 | **Playwright** |

로그인된 브라우저가 하는 일이 "글 열고 공감 누르기"뿐이므로, 검색을 훑는 행위가 계정과
분리되어 탐지 표면이 최소화된다. 143페이지 순회도 브라우저 렌더링 없이 끝난다.

## 4. 모듈 경계

```
like-bot-v2/
├── engine/                  ← UI를 전혀 모르는 순수 asyncio 코어
│   ├── paths.py             저장 위치 결정 (한 곳에서만)
│   ├── config.py            RunConfig · KeywordJob — 필드별 검증
│   ├── events.py            진행 이벤트 타입
│   ├── search.py            검색 API 페이지네이션 → 블로그 ID 스트림 (HTTP)
│   ├── posts.py             RSS 최신 글 목록 (HTTP)
│   ├── session.py           브라우저 기동 · 로그인 · storage_state
│   ├── like.py              공감 클릭 — 결과를 유형으로 반환
│   ├── ratelimit.py         계정 단위 토큰 버킷 + 지터
│   ├── safety.py            차단 감지 (연속 실패 · 성공률)
│   ├── history.py           SQLite 방문 기록 · 실행 이력
│   └── runner.py            생산자/소비자 오케스트레이션
├── desktop/                 ← PyQt6 (1단계)
│   ├── app.py
│   ├── bridge.py            asyncio 루프 ↔ Qt 시그널
│   └── widgets/
├── tests/
│   └── fixtures/            실측 응답 (검색 JSON · RSS XML)
└── data/                    .gitignore 대상
```

### 모듈별 책임

**`session.py`** — `storage_state`가 있으면 로드하고 **로그인 상태를 실제로 확인**한다.
유효하면 로그인 페이지를 지나가지 않는다. 무효할 때만 로그인하고 성공을 확인한 뒤 상태를
저장한다. 실패는 **캡차 / 2차인증 / 비밀번호 오류 / 세션 만료**로 구분해 올린다.
로그인이 확인되지 않으면 워커가 시작조차 하지 않는다.

**`search.py`** — 1순위로 JSON 응답을 파싱하고, 실패 시 DOM 선택자로 폴백한다. **폴백이
쓰였다는 사실 자체를 이벤트로 방출**한다(§7.4).

**`posts.py`** — RSS 우선. 실패 시 검색에서 받은 `seed_log_no` 하나로 폴백.

**`like.py`** — `frame_locator("#mainFrame")`로 iframe을 다루고, 결과를 유형으로 반환
한다(§7.1).

**`ratelimit.py`** — 워커 전원이 하나의 예산을 나눠 쓴다. 단일 이벤트 루프라 락이 없다.

**`history.py`** — 중복 방지와 실행 이력. SQLite. 조회·기록 모두 **로그인 계정 범위**로
한정된다(§6.4).

**`runner.py`** — 생산자/소비자 오케스트레이션과 종료 처리.

**`events.py`** — UI와의 유일한 접점. `WorkerStarted` / `PageCollected` / `BlogVisited` /
`LikeResult` / `FallbackUsed` / `Aborted` / `RunFinished`. 엔진은 이벤트를 방출할 뿐
누가 받는지 모른다.

## 5. 데이터 흐름

```
 ┌─ 생산자 (키워드마다 코루틴 1개) ────────────────┐
 │  page 1,2,3…  →  검색 API  →  중복 제거  →  put │──┐
 └───────────────────────────────────────────────┘  │
                                                     ▼
                                        대상 큐 (maxsize 제한)
                                                     │
 ┌─ 소비자 (1개, 브라우저 탭 1개) ─────────────────┐ │
 │  get → RSS → 속도제한 → 공감 → 기록 저장       │◀┘
 └───────────────────────────────────────────────┘
```

### 5.1 생산자 — 키워드 워커

```
for page in 1, 2, 3, ...:
    items = await search(keyword, start_date, end_date, page)
    if not items: break                            # 결정 2 · 결과 소진
    for it in items:
        if it.blog_id in seen_this_run: continue      # 실행 내 · 워커 간 중복
        if history.was_visited(account, it.blog_id): continue  # 결정 6 · 실행 간 중복
        seen_this_run.add(it.blog_id)
        await queue.put(Target(it.blog_id, keyword, seed_log_no=it.log_no))
```

**중복 제거는 큐 투입 전에 한다.** 소비자는 브라우저를 쓰는 유일한 지점이라 가장 비싸다.
걸러낼 대상이 거기까지 도달하면 그 비용을 헛되이 쓴다.

`seed_log_no`를 함께 넘기는 것은 RSS 실패 시의 폴백이다.

### 5.2 큐

`maxsize`를 제한한다(기본 50). 4키워드 × 143페이지 = 4000건을 미리 긁어둘 이유가 없다.
큐가 차면 생산자가 자연히 멈추므로 메모리를 쓰지 않고, 검색 요청도 소비 속도에 맞춰
자동 조절되며, 중단 시 버려지는 작업이 적다.

### 5.3 소비자 — 공감

```
while not stop_event.is_set():
    target = await queue.get()
    log_nos = await rss_recent(target.blog_id) or [target.seed_log_no]
    for log_no in log_nos[:like_num]:
        await rate_limiter.acquire()          # 공감 1건 = 토큰 1개
        result = await like.press(page, target.blog_id, log_no)
        emit(LikeResult(...))
        if result is BLOCKED: abort(); return
    history.record(target.blog_id, target.keyword, ...)
    budget.consume_blog()
```

RSS 조회를 생산자가 아니라 소비자에서 하는 이유는, 상한에 걸려 결국 처리되지 않을
대상까지 미리 조회하는 낭비를 없애기 위함이다. RSS는 0.3초 수준이라 공감 3건(10초
내외) 옆에서 무시할 만하다.

**속도 제한의 단위는 블로그가 아니라 공감 1건이다.** 계정이 실제로 받는 부하가 공감
횟수이기 때문이다.

### 5.4 종료 처리

| 사유 | 트리거 | 처리 |
|---|---|---|
| 상한 도달 | 방문 블로그 수 = 설정값 | 소비자 종료 → 생산자 취소 → 큐 폐기 |
| 결과 소진 | 모든 생산자 종료 + 큐 빔 | 소비자 종료 |
| 사용자 중단 | `stop_event` | 처리 중인 블로그를 끝까지 마치고 종료 |
| 차단 의심 | `like.press`가 `BLOCKED` 반환 | 즉시 전체 중단 |

집계는 `RunSummary` 하나에 계속 누적되고, **어떤 경로로 끝나든 그 값이 그대로 보고된다.**
레거시처럼 `return 0, 0, 0` 하는 경로가 존재하지 않는다(결함 6).

### 5.5 진행률

검색 API의 `totalCount`로 키워드별 실제 진행률을 표시한다. 1000이면 상한이므로 `1000+`로
표기한다.

### 6.1 저장 위치

```
%LOCALAPPDATA%\like-bot-v2\        (개발 중에는 ./data/)
├── config.json              실행 설정 — 비밀번호 없음
├── sessions\
│   └── {account}.dat        Playwright 세션 (계정별, 암호화)
└── history.db               SQLite — visits는 (account, blog_id) 기준
```

레거시는 `open("accounts.csv")`처럼 작업 디렉터리 상대 경로를 써서 exe를 다른 위치에서
실행하면 파일을 찾지 못했다. v2는 경로를 `paths.py` 한 곳에서 결정하고 나머지 모듈은
주입받는다. `data/`는 통째로 `.gitignore` 대상이다.

### 6.2 자격증명

`keyring`으로 OS 자격증명 저장소에 넣는다. Windows Credential Manager(DPAPI)는 로그인
사용자 계정에 묶어 암호화하므로, 파일이 유출돼도 다른 PC에서는 풀 수 없다.
`config.json`에는 **계정 ID만** 남는다.

엔진은 `CredentialStore` 인터페이스만 안다. 2단계 리눅스 서버는 데스크톱 키링 데몬이
없는 경우가 많으므로 환경변수 구현체로 교체한다.

세션 재사용이 되면 비밀번호를 쓰는 빈도 자체가 급감한다 — 자격증명은 세션 만료 시의
복구 수단에 가깝다.

### 6.3 세션

`storage_state`(쿠키 + localStorage)를 **계정별 파일로** 저장해 재사용한다. 단일 파일이면
계정을 바꿀 때마다 세션이 덮어써져 매번 로그인 폼을 다시 지나가게 되는데, 그곳이 가장
방어가 강하고 위험한 구간이므로 그 왕복 자체를 없애는 것이 요점이다.

**이 파일은 네이버 세션 쿠키이며, 훔치면 비밀번호 없이 로그인된다.** 자격증명을 키링에
넣고 세션을 평문 JSON으로 두면 보호가 반감되므로, Windows DPAPI로 암호화해 저장한다.
`SessionStore` 인터페이스 뒤에 두어 리눅스에서는 파일 권한 `0600`으로 대체한다.

### 6.4 방문 기록

```sql
CREATE TABLE visits (
    account     TEXT NOT NULL,      -- 공감을 누른 로그인 계정
    blog_id     TEXT NOT NULL,
    run_id      TEXT NOT NULL,
    keyword     TEXT NOT NULL,
    visited_at  TEXT NOT NULL,
    likes_ok    INTEGER NOT NULL,
    likes_tried INTEGER NOT NULL,
    outcome     TEXT NOT NULL,      -- liked | already | no_button | error
    PRIMARY KEY (account, blog_id)  -- 결정 6 · 중복 방지의 핵심
);

CREATE TABLE runs (
    run_id       TEXT PRIMARY KEY,
    started_at   TEXT NOT NULL,
    finished_at  TEXT,
    account      TEXT NOT NULL,
    keywords     TEXT NOT NULL,     -- JSON
    blogs_done   INTEGER NOT NULL,
    likes_ok     INTEGER NOT NULL,
    stop_reason  TEXT               -- budget | exhausted | user | blocked | error
);
```

**방문 기록은 로그인 계정 기준이다.** `(account, blog_id)` 복합 기본키이며, 중복 판정은
언제나 실행 중인 계정 범위 안에서만 이루어진다.

계정을 무시하고 `blog_id` 단독으로 판정하면, 계정 B로 처음 돌릴 때 계정 A가 이미 다녀온
블로그를 건너뛴다. 계정 B는 그 블로그에 한 번도 간 적이 없으므로 명백히 틀린 동작이고,
운영자가 블로그를 둘 이상 운영하거나 계정을 교체하는 순간 조용히 대상을 잃는다. 반대로
계정별로 분리해 두면 같은 DB 파일 하나로 여러 계정을 안전하게 운용할 수 있다.

복합 기본키는 SQLite에서 그대로 인덱스가 되므로 `WHERE account=? AND blog_id=?` 조회는
여전히 로그 시간이다. 생산자가 페이지마다 7건씩 하는 조회(§5.1)에 부담이 없다.

같은 이유로 `history` 인터페이스는 계정을 명시적으로 받는다 —
`was_visited(account, blog_id)`. 기본값으로 숨기지 않는다.

공감 1건마다 남기는 상세 이벤트 테이블은 **의도적으로 만들지 않는다.** 답방률을 실제로
측정하려면 내 블로그 유입 로그가 필요한데 그것은 네이버 통계에만 있고 가져올 수 없다.
기록 가능한 것은 "언제 누구에게 갔나"까지이며 `visits`의 날짜로 충분하다.

쓰기는 소비자 코루틴 한 곳에서만, 블로그 1개당 1회 일어난다. 로컬 SQLite 쓰기는
마이크로초 수준이라 비동기 래퍼 없이 동기 호출로 충분하다. 다만 2단계 웹 UI가 실행 중인
DB에 읽기 전용으로 붙을 수 있도록 **WAL 모드**로 연다.

### 6.5 설정

`config.json`에 키워드 목록, 기간, 방문 상한, 블로그당 공감 수, 속도 제한, 제외 단어
(레거시 `exclude.csv` 통합)를 담는다.

레거시는 `except ValueError` 하나가 8개 필드를 전부 폴백값으로 되돌렸고, 그 폴백값이
UI 표시값과 달랐다(공감 수 3 vs 2, Depth 1 vs 2, 목표 9999 vs 300, 끝 페이지 572 vs 400).
v2는 `config.py`의 값 객체가 **필드마다 개별 검증**하고 잘못된 필드만 그 자리에 오류를
표시한다. 기본값은 한 곳에만 정의되어 UI와 엔진이 같은 값을 본다.

## 7. 오류 처리 · 안전장치

### 7.1 공감 결과 유형

| 결과 | 대응 | 속도 토큰 |
|---|---|---|
| `SUCCESS` | 카운트, 계속 | 소비 |
| `ALREADY_LIKED` | 정상 상황. 스킵, 계속 | 소비 안 함 |
| `NO_BUTTON` | 정상 상황(비공개·삭제·공감 비허용). 스킵 | 소비 안 함 |
| `TIMEOUT` | 1회 재시도 → 실패 시 이 글만 스킵 | 소비 |
| `NOT_LOGGED_IN` | 세션 복구 1회 시도 → 실패 시 전체 중단 | — |
| `BLOCKED` | **즉시 전체 중단. 재시도 금지** | — |
| `ERROR` | 이 글 스킵. 연속 임계 초과 시 중단 | 소비 |

레거시는 이 일곱을 `"공감 없음 or 이미 함"` 한 줄로 뭉갰다. 유형을 나누는 이유는 표시가
아니라 대응이 각각 다르기 때문이다. 차단 상태에서의 재시도는 상황을 악화시킬 뿐이다.

### 7.2 차단 감지

네이버가 제한을 걸 때 정확히 어떤 신호를 주는지는 확인되지 않았다. 실제로 겪어야 아는
영역이므로 두 층으로 나눈다.

**직접 신호** — 구현하되 이것만 믿지 않는다: 캡차 페이지 리다이렉트, 로그인 페이지로의
튕김, "일시적으로 제한" 류 문구, 공감 요청의 오류 응답.

**간접 신호** — 실질적인 안전망: 최근 N건 연속 실패 시 원인 불문 중단, 최근 20건의
성공률이 임계 이하로 떨어지면 중단.

간접 신호가 핵심인 이유는 **네이버가 어떤 방식으로 막든 "갑자기 안 되기 시작함"은
공통**이기 때문이다. 네이버의 내부 구현을 몰라도 동작하고, 그 구현이 바뀌어도 계속
동작한다. 직접 신호는 정확도를 높이는 보조이며, 안전은 간접 신호가 책임진다.

### 7.3 속도 제한

토큰 버킷에 지터를 건다. 정확히 일정한 간격은 그 규칙성 자체가 봇 신호이므로 실제
간격은 기준값에 무작위 계수를 곱한다. 블로그를 바꿀 때는 조금 더 쉰다.

레거시의 `Latency` 노브를 이어받되, Playwright의 auto-waiting이 "요소 대기" 역할을
가져가므로 이제 **"사람처럼 보이는 간격"만** 담당한다.

기본값은 보수적으로(분당 한 자릿수) 잡는다. **네이버의 실제 임계는 공개되어 있지 않고
계정 이력에 따라서도 다르므로, 이 값이 정답이라고 단정할 수 없다.** 낮게 시작해 운영하며
조정하는 것이 유일하게 안전한 방법이고, 그래서 설정 파일에서 바로 조절 가능해야 한다.

### 7.4 폴백을 사건으로 취급

레거시가 죽은 경로는 "파싱 실패 → 조용히 값을 하드코딩 → 아무도 모른 채 계속 동작"이었다.

v2는 폴백이 **작동했다는 사실 자체를 이벤트로 방출**한다.

- 검색 JSON 파싱 실패 → DOM 폴백 → `FallbackUsed` → UI에 눈에 띄게 표시
- RSS 실패 → `seed_log_no` 하나만 사용 → 로그
- 폴백 비율이 임계를 넘으면 경고

조용히 잘리는 대신 시끄럽게 알린다.

### 7.5 오류 전파 경계

```
글 하나 실패      →  그 글만 스킵, 다음 글로
블로그 하나 실패  →  그 블로그만 스킵, 다음 블로그로
세션 · 차단 실패  →  전체 중단
```

레거시는 광범위한 `except Exception`이 중단해야 할 것과 넘어가야 할 것을 같이 삼켰다.
v2는 계층마다 무엇을 잡고 무엇을 올려보낼지 명시한다.

### 7.6 로그

**UI 로그** — 사람이 읽는 것. 키워드별 패널에 간결하게.
**파일 로그** — 진단용. JSON Lines로 요청 URL, 응답 코드, 결과 유형, 소요 시간, 예외 스택.

예외를 삼키고 넘어가더라도 파일 로그에는 전체 맥락을 남긴다. 레거시는 `"블로그 처리 중
오류"` 한 줄만 남겨 사후 원인 파악이 불가능했다.

비밀번호와 세션 쿠키는 어느 로그에도 남기지 않는다. `blog_id`는 남긴다.

## 8. 테스트 전략

검색·글목록을 브라우저에서 분리한 결과 **파서가 순수 함수가 되어 브라우저 없이
테스트된다.** 레거시는 모든 파싱이 살아 있는 Selenium 세션 안에 있어 테스트가 불가능했다.

### 층 1 — 순수 로직 (네트워크·브라우저 없음)

| 대상 | 검증 내용 |
|---|---|
| `config.py` | 필드별 개별 검증 — 한 필드 오류가 나머지를 리셋하지 않는가 |
| 검색 응답 파서 | `)]}',` 접두사 제거, `searchList` 추출, 빈 페이지 판정 |
| RSS 파서 | CDATA로 감싸인 `<link>`에서 글 번호 추출 |
| `ratelimit.py` | 가짜 시계 주입으로 간격·지터를 결정론적으로 |
| `history.py` | 임시 SQLite로 중복 판정, 재실행 시 스킵 |
| `safety.py` | 결과 시퀀스 주입 — 연속 실패·성공률 임계에서 정확히 발동하는가 |
| `runner.py` | 가짜 검색소스 + 가짜 공감기로 **4가지 종료 경로 전부** |

RSS 파서가 표에 있는 이유: 설계 검증 과정에서 CDATA를 놓쳐 "RSS 전부 실패"라는 틀린
결론을 냈다가 원문을 확인하고 정정했다. 정확히 그런 실수를 잡는 층이다.

`runner.py` 테스트가 특히 중요하다. 결함 6은 **종료 경로마다 집계가 보존되는가**의
문제이며 가짜 부품으로 완전히 검증할 수 있다.

픽스처는 2026-08-30 실측에서 받은 검색 JSON과 RSS XML을 그대로 쓴다.

### 층 2 — 계약 테스트 (네트워크 O, 로그인 X)

네이버가 바뀌었는지 감지하는 조기 경보다.

- 검색 API가 여전히 `totalCount` / `pagePerCount` / `searchList[].domainIdOrBlogId` /
  `logNo`를 주는가
- RSS가 여전히 파싱되는가
- 빈 페이지 동작이 여전한가 (144페이지 → 0건)

비로그인이라 계정 위험 없이 돌릴 수 있다. 외부 의존이므로 CI 빌드를 막지 않고, 실패 시
"네이버가 바뀌었다"를 알리는 용도로만 쓴다. 결함 1이 반년 넘게 방치된 이유가 이런 감지
수단의 부재였다.

### 층 3 — 브라우저 · 드라이런

공감 클릭은 자동 테스트가 사실상 불가능하다. 진짜 계정으로 진짜 공감을 눌러야 하고,
취소해도 상대에게 알림이 갔을 수 있다. 억지로 자동화하면 테스트 자체가 계정 위험이 된다.

대신 **드라이런 모드**를 만든다 — 로그인하고, 글을 열고, 공감 버튼을 **찾는 데까지만**
하고 클릭하지 않는다. 셀렉터 유효성·iframe 전환·로그인 생존을 부작용 없이 확인한다.

드라이런은 운영 수단이기도 하다. 새 키워드로 본격 실행하기 전에 어떤 블로그들이 잡히는지
미리 볼 수 있다. §5에서 대상 발굴과 공감을 분리한 구조가 이를 자연스럽게 만든다.

### 하지 않을 것

- 네이버를 흉내내는 목 서버 — 유지 비용이 얻는 것보다 크다
- 브라우저 E2E 자동화 스위트 — 층 3과 같은 이유
- 커버리지 목표 숫자 — 위 표의 항목이 실제로 검증되는지가 기준이다

### TDD 적용 범위

층 1은 테스트를 먼저 쓴다. 입출력이 명확하고 픽스처도 있다.

층 3은 TDD가 맞지 않는다. 셀렉터가 맞는지는 실물을 열어봐야만 알 수 있어 "테스트를 먼저
쓴다"가 성립하지 않는다. 드라이런으로 확인하고 고치는 순환이 맞다. 이 구분을 흐리지 않는다.

## 9. 이번 작업의 범위

**포함**: `engine/` 전체, `desktop/` PyQt6 UI, 층 1·2 테스트, 드라이런 모드.

**제외**: 웹 UI, 리눅스 서버 배포, headless 운용, 스케줄러(결정 7 — 별도 작업).

**PyQt6 UI 요구사항**: 절대좌표를 레이아웃 매니저로 교체(DPI·창 크기 대응), 키워드별
패널 구조를 실제로 배선(레거시의 전역 공유 문제 해소), 폴백·차단 경고를 눈에 띄게 표시,
필드별 검증 오류를 그 자리에 표시.

## 10. 2단계(웹·리눅스)로 가는 경로

엔진이 UI를 모르므로 2단계에서 엔진은 손대지 않는다.

- `events.py`의 이벤트를 웹소켓으로 중계하는 어댑터를 추가한다
- `CredentialStore`를 환경변수 구현체로 교체한다
- `SessionStore`를 파일 권한 방식으로 교체한다
- 브라우저를 headless로 전환한다 — **1단계에서 headful로 검증을 마친 뒤에만**
- `history.db`를 WAL 모드로 열어 두었으므로 웹이 읽기 전용으로 붙는다

지금 웹을 만들지 않는 것이 나중에 웹을 만드는 비용을 늘리지 않는다.
